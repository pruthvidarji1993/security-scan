Executive summary

This service exposes an orders lookup endpoint that is unsafe in two serious ways. First, the order identifier from the web address is placed directly into a database command, which lets an attacker rewrite that command and read, alter, or delete the entire orders database - a full data breach from a single crafted link. Second, the endpoint performs no login or ownership check, so anyone on the internet can request any order by number and receive another customer's order details.

Together these allow complete exposure of customer order data with no credentials required. We recommend fixing the database query to use safe parameters and adding an authentication and ownership check before this endpoint is exposed to any real traffic. These are the first and most urgent items to address.

Findings

critical

Unauthenticated IDOR: any order readable by id

confirmed

app/api/orders/[id]/route.ts:4 · ai · A01 · CWE-862 · A001

The GET handler performs no authentication and no ownership check. It loads the order purely by the id in the URL, so any anonymous caller can enumerate ids and read any customer's order.

Attack path: params.id (route.ts:4) -> pool.query (route.ts:5) -> rows[0] returned (route.ts:6); no session, no user filter

Example request: GET /api/orders/1, then /api/orders/2 ... with no cookie returns every customer's order

Fix: Authenticate the request, then scope the query to the caller (WHERE id = $1 AND user_id = $2) and return 404 when no row matches.

critical

SQL injection in the order lookup

confirmed

app/api/orders/[id]/route.ts:5 · ai · A03 · CWE-89 · A002

The id from the URL is inserted into the SQL text with a template string instead of a parameter.

Attack path: params.id (route.ts:4) -> template string -> pool.query (route.ts:5)

Example request: GET /api/orders/1%20OR%201=1 returns every order

Fix: Use a parameterised query: pool.query('SELECT * FROM orders WHERE id = $1', [params.id]).

low

No security headers configured

confirmed

next.config.js · ai · A05 · CWE-693 · A003

The app sets no Content-Security-Policy, X-Content-Type-Options or Referrer-Policy headers.

Fix: Add a headers() block in next.config.js.
