Overall risk: Critical

Executive summary

This service exposes an orders lookup endpoint that is unsafe in two serious ways. First, the order identifier from the web address is placed directly into a database command, which lets an attacker rewrite that command and read, alter, or delete the entire orders database - a full data breach from a single crafted link. Second, the endpoint performs no login or ownership check, so anyone on the internet can request any order by number and receive another customer's order details.

Together these allow complete exposure of customer order data with no credentials required. We recommend fixing the database query to use safe parameters and adding an authentication and ownership check before this endpoint is exposed to any real traffic. These are the first and most urgent items to address.

Findings

critical

Unauthenticated IDOR: any order readable by id

confirmed

app/api/orders/[id]/route.ts:2 · ai · A01 · CWE-862 · A002

The GET handler performs no authentication and no ownership check. It loads the order purely by the id in the URL, so any anonymous caller can enumerate ids and read any customer's order. There is no session lookup and no filter tying the order to the caller.

Fix: Authenticate the request (verified session), then scope the query to the caller - e.g. WHERE id = $1 AND user_id = $2 - and return 404 when no row matches, so existence is not revealed.

critical

SQL injection via order id in GET /api/orders/[id]

confirmed

app/api/orders/[id]/route.ts:3 · ai · A03 · CWE-89 · A001

The route interpolates params.id straight into a SQL string: db.query(`SELECT * FROM orders WHERE id = ${params.id}`). params.id is attacker-controlled from the URL path and is never validated or escaped. A request such as GET /api/orders/0%20OR%201=1 returns all orders; with stacked queries or UNION the attacker can read other tables, and depending on the driver modify or drop data.

Fix: Use a parameterised query instead of string interpolation, e.g. db.query('SELECT ... FROM orders WHERE id = $1', [params.id]) (or the driver's placeholder syntax), and validate that params.id is the expected type (numeric/UUID) before use.

low

SELECT * serialises every order column to the client

confirmed

app/api/orders/[id]/route.ts:3 · ai · A01 · CWE-213 · A003

The handler returns the raw row from SELECT * directly as JSON, so any internal or sensitive columns on the orders table (internal notes, cost, payment references, flags) are sent to the client. This is a lesser issue than the injection and missing authorization above, but it widens what those expose.

Fix: Select only the columns the client needs (SELECT id, status, total, ... ) or map the row to an explicit response shape before returning it.

Scope and limitations

Full-repository review of the 'nextjs' project (stacks: next, node, react). The repository contains a single application source file, the orders route handler at app/api/orders/[id]/route.ts, plus package.json. Checklists applied: general, nextjs, react, node-api.

web-secure-verification did not run because node_modules is missing (dependencies were not installed; installing them runs arbitrary package scripts, so this was intentionally skipped). The referenced data layer @/lib/db is not present in the repository, so the database client's own behaviour (parameterisation, connection scoping) could not be inspected; findings are based on how the route calls it. No authentication, session, or configuration code exists in the repository to review, so broader auth/session and header hardening could not be assessed beyond this one endpoint.
